# Ad hoc error interfaces

## Proposition

Add an `ad_hoc_error_interfaces` lint for local error types that participate in `Result` but expose
messages and causes through private conventions instead of `Display` and `std::error::Error`.

```rust
// Bad: generic error consumers cannot inspect or report this failure.
struct ParseFailure {
    message: String,
    cause: Option<io::Error>,
}

impl ParseFailure {
    fn message(&self) -> &str {}
    fn cause(&self) -> Option<&io::Error> {}
}
```

```rust
// Better: presentation and causal chaining use standard interfaces.
impl Display for ParseFailure {
    fn fmt(&self, formatter: &mut Formatter<'_>) -> fmt::Result {
        formatter.write_str(&self.message)
    }
}

impl Error for ParseFailure {
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        self.cause.as_ref().map(|cause| cause as _)
    }
}
```

## Why this matters

Generated code frequently invents error containers that compile for one call chain but lose
interoperability with reporting, context, source traversal, and generic error bounds. Standard
traits make the contract explicit without prescribing a particular error-handling crate.

An `Error` implementation requires `Debug` and `Display`. Its `source` method expresses causal
chaining; it should not be fabricated merely because a type has a field named `cause`.

## Conservative detection

- Find local types used as the error parameter of `Result<T, E>`.
- Increase confidence when type names end with `Error`, `Failure`, or project-configured error
  vocabulary.
- Increase confidence for fields or accessors named `message`, `cause`, `source`, `inner`, or
  `context`.
- Check whether `Debug`, `Display`, and `Error` are already implemented directly or through a derive
  macro.
- Diagnose missing `Display` separately from missing `Error` when only presentation is proven.
- Diagnose ad hoc causal accessors when a real underlying error can be exposed through
  `Error::source`.
- Exclude types generated by external macros or schemas.

## Error-like values that are not Error

```rust
enum ValidationIssue {
    MissingField,
    InvalidValue,
}

struct Diagnostic {
    severity: Severity,
    message: String,
}
```

Validation issues, diagnostics, protocol rejection values, and user-facing form errors may be data
rather than failures in Rust's causal error model. Use in `Result` is strong evidence but not proof:
some APIs intentionally return structured non-error rejection information.

The lint should avoid requiring `Error` when the type is accumulated, serialized, compared as data,
or presented alongside successful partial output.

## Derived implementations

Libraries such as `thiserror` can produce lawful implementations. The lint should inspect expanded
trait implementations while attaching diagnostics only to authored source. It must not demand
manual boilerplate when a derive already supplies the standard interface.

Conversely, a derive annotation that omits a source relationship may still leave an ad hoc `cause`
method. The rule can point out the missing causal contract without prescribing a specific library.

## Error source semantics

Not every nested error is the causal source. Aggregates and peer failures require explicit design:

```rust
struct BatchFailure {
    failures: Vec<ItemError>,
}
```

`Error::source` exposes one causal predecessor, not an arbitrary collection. The lint should not
recommend choosing the first nested error. A named iterator over component failures may be the
correct API.

## Interaction with other rules

- `ad_hoc_formatting` can recognize missing `Display`, but this rule supplies error-specific
  guidance and protects secrets or structured diagnostics.
- `discarded_results` preserves errors long enough for their standard interface to matter.
- `constructor_like_free_functions` and `ad_hoc_conversions` should treat error construction as
  ordinary construction only when the semantic conversion laws hold.
- `undocumented_items` ensures the public error contract explains recovery and source semantics.

## Open decisions

- Whether every private type used in `Result` must implement `Error`.
- Whether a type name ending in `Error` is sufficient evidence without observed `Result` use.
- How to distinguish diagnostic data from causal errors reliably.
- Whether missing `source` should warn when a nested error is present but intentionally contextual.
- Whether the rule should require `'static` sources or accept advanced borrowed error designs.
