# `rlib::bidirectional_module_dependencies`

## Summary

Finds sibling modules that import from each other in both directions.

## At a glance

| Field | Value |
| --- | --- |
| Group | `rlib::core` |
| Cargo feature | always |
| Purpose | Code clarity |
| Default level | `warn` |
| Fix | Manual |

## What it catches

Finds sibling modules that import from each other in both directions. Dependencies between
parents and children are not considered because child modules routinely use names defined by
their parent. Imports hand-written by local macros participate; imports generated by external macros
are excluded because their source cannot be repaired in the linted crate.

## Why this matters

A two-way dependency leaves neither sibling as the lower-level abstraction. Moving shared
concepts into a neutral module or choosing one dependency direction makes ownership clearer
and lets either side evolve without preserving an accidental cycle.

## Examples

### Triggers the lint

```rust
mod parser {
    use super::syntax::Syntax;
    pub struct Parser(pub Syntax);
}
mod syntax {
    use super::parser::Parser;
    pub struct Syntax;
    impl Syntax { fn parse(_: Parser) {} }
}
```

### Use this instead

Extract shared concepts or move the coordinating behavior so imports flow one way:

```rust
mod syntax { pub struct Syntax; }
mod parser {
    use super::syntax::Syntax;
    pub struct Parser(pub Syntax);
}
```

## What it skips

Dependencies between parents and children are not considered because child modules routinely use names defined by their parent.

## When to turn it off

Turn this lint off when the current structure is clearer for your team.

## Settings

This lint has no behavior-specific settings.
